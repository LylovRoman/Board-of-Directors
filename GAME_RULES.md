# Board of Directors - подробные правила игры

Этот документ описывает правила так, как они сейчас реализованы в проекте. Это не только "лор" для игрока, но и практическая спецификация текущей механики backend/frontend.

## Коротко об игре

**Board of Directors** - скрыторолевая корпоративная игра про совет директоров.

Игроки входят в комнату, получают доли компании, выбирают мажорные решения и после каждого принятого решения проводят раунд корпоративных маневров. Среди директоров есть один тайный **Крот**. Его задача - провести через совет набор вредных для компании решений. Остальные игроки - **Директора**. Их задача - принять достаточно безопасных решений раньше, чем Крот выполнит свои цели.

Игра построена вокруг долей владения. Голоса считаются не по количеству игроков, а по суммарной доле голосовавших игроков.

## Основные сущности

### Игрок

Игрок - пользователь с именем. Авторизация пока временная: frontend хранит `current_user_id` в `localStorage`, а API получает `user_id` / `viewer_user_id` явно.

Игрок может:

- создать комнату;
- присоединиться к комнате;
- выйти из лобби до старта;
- писать в игровой чат;
- голосовать в активных фазах;
- подавать или пропускать corporate governance предложения;
- быть Host;
- быть CEO;
- быть Директором или Кротом после старта игры.

### Комната / игра

Игра имеет название и статус:

- `lobby` - комната создана, игра еще не началась;
- `started` - игра идет;
- `finished` - игра завершена.

В игре может быть от 3 до 8 активных игроков.

### Host

Host - игрок, который управляет лобби до старта.

Host может:

- начать игру;
- убрать игрока из лобби кнопкой kick.

Host не может кикнуть самого себя.

Если Host выходит из лобби до старта, Host автоматически передается следующему оставшемуся активному игроку. Если комната опустела, первый игрок, который снова войдет в эту комнату, станет Host.

Если в лобби не осталось игроков, игра удаляется из списка игр.

### CEO

CEO - особый игрок, выбранный при старте игры.

CEO:

- участвует в голосованиях обычной долей;
- не может воздерживаться ни в мажорном голосовании, ни в governance voting;
- решает ничьи, если его голос находится среди лидирующих вариантов;
- может быть сменен governance предложением `appoint_ceo`.

Назначить CEO уже действующего CEO нельзя.

### Роли

После старта игры каждый активный игрок получает одну из ролей:

- **Директор** - обычный член совета директоров;
- **Крот** - тайный саботажник.

Крот выбирается случайно. Остальные игроки считаются директорами.

Роль видна самому игроку. Цели Крота видны только Кроту.

## Доли и казначейский резерв

Вся компания представлена как `10000 bps`, то есть 100%.

В коде доли хранятся в basis points:

- `100 bps` = 1%;
- `500 bps` = 5%;
- `10000 bps` = 100%.

На старте игры:

- игроки суммарно получают 80%;
- казначейский резерв получает 20%.

Резерв называется в UI **Казначейский резерв**.

### Стартовые доли

Доли зависят от количества игроков:

| Игроков | Доли игроков | Резерв |
|---:|---|---:|
| 3 | 35%, 25%, 20% | 20% |
| 4 | 25%, 20%, 20%, 15% | 20% |
| 5 | 20%, 17%, 16%, 14%, 13% | 20% |
| 6 | 17%, 15%, 13%, 12%, 12%, 11% | 20% |
| 7 | 14%, 12%, 12%, 11%, 11%, 10%, 10% | 20% |
| 8 | 12%, 11%, 11%, 10%, 10%, 9%, 9%, 8% | 20% |

Порядок распределения долей привязан к случайно перемешанному списку игроков при старте.

### Минимальная доля игрока

Игрок не может быть опущен ниже 5% доли при governance маневрах:

- нельзя передать долю от игрока, если после передачи у него останется меньше 5%;
- нельзя выкупить долю игрока в резерв, если после выкупа у него останется меньше 5%.

### Максимальный размер governance изменения

Один governance маневр с долями может менять не больше 5%:

- `share_transfer` - максимум 5%;
- `treasury_grant` - максимум 5%;
- `treasury_buyback` - максимум 5%.

## Решения A-H

В механике решения хранятся как буквы `A-H`. В интерфейсе они показываются атмосферными названиями:

| ID | Название |
|---|---|
| A | Враждебное поглощение |
| B | Экспансия на новый рынок |
| C | Выплата дивидендов по акциям |
| D | Запуск экспериментального продукта |
| E | Сделка слияния |
| F | Оптимизация неэффективного персонала |
| G | Агрессивная налоговая стратегия |
| H | Обратный выкуп акций |

В начале игры все 8 решений доступны.

Когда мажорное решение принято, оно удаляется из списка доступных решений и больше не может быть выбрано в следующих мажорных раундах.

## Старт игры

Host может начать игру только если в комнате от 3 до 8 активных игроков.

При старте происходят события:

1. Игра переходит в статус `started`.
2. Случайно выбирается Крот.
3. Случайно выбираются 3 цели Крота из решений A-H.
4. Игрокам распределяются стартовые доли.
5. Случайно выбирается CEO.
6. Начинается первый мажорный раунд голосования.

## Общий цикл партии

Партия идет циклами:

1. **Мажорное голосование** - игроки выбирают одно из решений A-H или воздерживаются.
2. Если мажорное решение принято:
   - оно попадает в историю принятых решений;
   - игроки, голосовавшие за принятое решение, получают бонус из резерва;
   - проверяется победа;
   - если победителя нет, начинается governance proposal phase.
3. **Раунд корпоративных маневров: подача предложений** - каждый игрок может подать одно предложение или пропустить.
4. Если предложений нет, сразу начинается следующий мажорный раунд.
5. Если предложения есть, начинается governance voting phase.
6. **Раунд корпоративных маневров: голосование** - игроки голосуют за одно предложение или воздерживаются.
7. Победившее governance предложение применяется, либо отклоняется при ничьей/отсутствии голосов.
8. Начинается следующий мажорный раунд.

Если после принятого мажорного решения уже есть победитель, governance раунд не запускается.

## Мажорное голосование

Фаза в коде: `major_voting`.

Каждый активный игрок может один раз:

- проголосовать за доступное решение;
- или воздержаться, если он не CEO.

CEO не может воздерживаться.

Игрок не может изменить голос в рамках текущего мажорного раунда.

Раунд считается готовым к разрешению, когда проголосовали все активные игроки.

### Как считается победитель мажорного голосования

Голоса считаются по долям игроков.

Если игрок проголосовал за решение, его текущая доля прибавляется к score этого решения.

Воздержавшиеся:

- считаются проголосовавшими для завершения раунда;
- не добавляют долю ни к одному решению.

После голосов всех активных игроков:

1. Backend находит решение или решения с максимальной суммарной долей.
2. Если лидер один, это решение принимается.
3. Если лидеров несколько, проверяется голос CEO.
4. Если CEO голосовал за один из лидирующих вариантов, принимается вариант CEO.
5. Если CEO не голосовал за лидера, мажорное решение не принимается.

Причина непринятия при ничьей: `tie_not_resolved`.

Если никто не отдал голос за конкретное решение, то решение тоже не принимается и начинается следующий мажорный раунд.

### Бонус за принятое мажорное решение

После принятия мажорного решения все активные игроки, которые голосовали именно за это решение, получают бонус из казначейского резерва.

Базовый бонус:

- 1% каждому такому игроку.

Технически это `100 bps`.

Если резерва не хватает на полный бонус всем, backend уменьшает бонус так, чтобы резерв не ушел ниже 0. Бонус делится поровну между игроками, голосовавшими за принятое решение, с округлением вниз до целых bps.

Если итоговый бонус получается 0 bps, бонусные события не создаются.

## История мажорных раундов

Для каждого завершенного мажорного раунда backend строит отчет.

В отчете видны:

- номер раунда;
- принято решение или нет;
- принятое решение, если оно есть;
- причина непринятия, если решения нет;
- распределение голосов по вариантам;
- суммарная доля каждого варианта;
- количество игроков, голосовавших за каждый вариант.

Выбор конкретного игрока в общем списке current votes не раскрывается. Но детальный отчет раунда показывает агрегированную картину: какие варианты получали голоса и какую долю набрали.

## Раунд корпоративных маневров

UI-название: **Раунд корпоративных маневров**.

Кодовое название: `governance`.

Governance раунд запускается после каждого принятого мажорного решения, если игра еще не завершена.

Governance состоит из двух возможных фаз:

1. `governance_proposal` - игроки подают предложения или пропускают.
2. `governance_voting` - игроки голосуют за поданные предложения.

## Governance proposal phase

Фаза в коде: `governance_proposal`.

Каждый активный игрок может ровно один раз:

- подать одно governance предложение;
- или пропустить.

Предложение или пропуск нельзя изменить в MVP.

Когда все активные игроки подали предложение или пропустили:

- если предложений нет, сразу начинается следующий мажорный раунд;
- если есть хотя бы одно предложение, начинается governance voting phase.

## Типы governance предложений

### 1. Передача доли

Код: `share_transfer`.

Смысл: передать часть доли от одного игрока другому.

Payload:

```json
{
  "proposal_type": "share_transfer",
  "from_user_id": 1,
  "to_user_id": 2,
  "share_bps": 500
}
```

Ограничения:

- `from_user_id` и `to_user_id` обязательны;
- нельзя передать долю самому себе;
- оба игрока должны быть активными;
- размер передачи должен быть больше 0;
- размер передачи не может превышать 5%;
- после передачи у отправителя должно остаться минимум 5%.

Эффект при принятии:

- у `from_user_id` доля уменьшается;
- у `to_user_id` доля увеличивается;
- казначейский резерв не меняется.

### 2. Грант из резерва

Код: `treasury_grant`.

Смысл: выдать игроку долю из казначейского резерва.

Payload:

```json
{
  "proposal_type": "treasury_grant",
  "target_user_id": 2,
  "share_bps": 500
}
```

Ограничения:

- `target_user_id` обязателен;
- целевой игрок должен быть активным;
- размер гранта должен быть больше 0;
- размер гранта не может превышать 5%;
- казначейский резерв не может уйти ниже 0.

Эффект при принятии:

- казначейский резерв уменьшается;
- доля целевого игрока увеличивается.

### 3. Выкуп доли в резерв

Код: `treasury_buyback`.

Смысл: выкупить часть доли игрока обратно в казначейский резерв.

Payload:

```json
{
  "proposal_type": "treasury_buyback",
  "target_user_id": 2,
  "share_bps": 500
}
```

Ограничения:

- `target_user_id` обязателен;
- целевой игрок должен быть активным;
- размер выкупа должен быть больше 0;
- размер выкупа не может превышать 5%;
- после выкупа у игрока должно остаться минимум 5%.

Эффект при принятии:

- казначейский резерв увеличивается;
- доля целевого игрока уменьшается.

### 4. Назначить CEO

Код: `appoint_ceo`.

Смысл: назначить нового CEO.

Payload:

```json
{
  "proposal_type": "appoint_ceo",
  "target_user_id": 3
}
```

Ограничения:

- `target_user_id` обязателен;
- целевой игрок должен быть активным;
- нельзя назначить CEO уже действующего CEO.

Эффект при принятии:

- CEO становится целевой игрок.

## Governance voting phase

Фаза в коде: `governance_voting`.

Каждый активный игрок может один раз:

- проголосовать за одно из предложений;
- или воздержаться, если он не CEO.

CEO не может воздерживаться.

Игрок не может изменить голос в рамках текущего governance голосования.

Фаза завершается, когда все активные игроки проголосовали.

### Как считается победитель governance голосования

Governance голосование считается по тем же принципам, что и мажорное:

1. Голоса считаются по долям игроков.
2. Воздержавшиеся не дают долю ни одному предложению.
3. Если одно предложение набрало больше всех долей, оно принимается.
4. Если несколько предложений делят первое место, проверяется голос CEO.
5. Если CEO голосовал за одно из лидирующих предложений, принимается предложение CEO.
6. Если CEO не выбрал лидера или голосов за предложения нет, governance предложение не принимается.

Причина отклонения governance предложения: `tie_or_no_votes`.

После разрешения governance voting всегда начинается следующий мажорный раунд.

## Условия победы

Победа проверяется после принятого мажорного решения.

### Победа Крота

Крот побеждает, если все 3 его тайные цели среди мажорных решений были приняты.

Backend winner: `mole`.

Причина: `mole_targets_collected`.

### Победа Совета директоров

Совет директоров побеждает, если принято 3 "чистых" решения, то есть 3 решения, которые не являются целями Крота.

Backend winner: `players`.

Причина: `three_clean_decisions_collected`.

### Важное следствие

Если мажорное решение принято и сразу выполняется условие победы, игра завершается немедленно. Governance раунд после такого решения не запускается.

## Крот и цели

Крот получает 3 цели из списка A-H.

Цели:

- выбираются случайно при старте;
- сортируются по буквам;
- видны только Кроту;
- в UI для Крота подсвечиваются варианты голосования, которые помогают его целям.

Остальные игроки не видят цели Крота и не знают, кто Крот, кроме косвенных выводов по поведению.

## Чат

В игре есть общий чат комнаты.

Правила:

- писать могут только активные игроки комнаты;
- сообщение обрезается по пробелам по краям;
- пустое сообщение отправить нельзя;
- максимальная длина сообщения - 500 символов;
- публичное состояние возвращает последние 80 сообщений;
- чат доступен в лобби, во время игры и на финальном экране.

## Лобби, выходы и удаление пустых комнат

До старта игры игрок может выйти из лобби.

Frontend также пытается автоматически отправить `leave_game`, если игрок закрывает вкладку браузера, находясь в лобби еще не начатой игры.

Выход из лобби:

- не является киком;
- убирает игрока из активного списка комнаты;
- позволяет игроку вернуться через обычное присоединение;
- если ушел Host, Host передается следующему активному игроку;
- если после выхода не осталось игроков, комната удаляется из списка игр.

Кик отличается от выхода:

- кикнуть может только Host;
- кик работает только до старта;
- кикнутый игрок может вернуться в эту же комнату через обычное присоединение.

Бан отличается от кика:

- забанить может только Host;
- бан работает только до старта;
- забаненный игрок не может вернуться в эту же комнату.

После старта игры выйти из игры через `leave_game` нельзя.

## Доступные действия

Backend возвращает `available_actions` персонально для viewer user.

Примерный смысл:

- `join_game` - игрок не в активном лобби или вышел из него и может присоединиться;
- `leave_game` - игрок активен в лобби и может выйти;
- `kick_player` - viewer является Host в лобби;
- `ban_player` - viewer является Host в лобби;
- `start_game` - viewer является Host в лобби;
- `send_chat_message` - viewer является активным игроком комнаты;
- `vote` - viewer может голосовать в текущей voting фазе;
- `submit_governance_proposal` - viewer может подать governance предложение;
- `skip_governance_proposal` - viewer может пропустить governance proposal phase.

Для завершенной игры новые игровые действия в основном недоступны, но активный игрок все еще может отправлять сообщения в чат, если backend считает его активным игроком.

## Публичное и персональное состояние

Состояние игры персонализировано под viewer user.

В публичном состоянии видны:

- список активных игроков;
- доли игроков;
- Host и CEO бейджи;
- статус игры;
- текущая фаза;
- текущий раунд;
- казначейский резерв;
- доступные решения;
- принятые решения;
- агрегированные статусы голосования;
- governance предложения;
- governance отчеты;
- отчеты мажорных раундов;
- чат.

Персонально viewer получает:

- `me`;
- свою роль;
- цели Крота, если viewer является Кротом;
- свой текущий голос в текущей фазе.

Технические поля вроде выбора других игроков в текущем голосовании не должны раскрываться напрямую. Для текущих голосов публично показывается только факт: игрок уже проголосовал или еще ожидается.

## Событийная модель

Backend хранит игру как историю событий.

Состояние не считается главным источником правды. Оно восстанавливается из событий.

Основные события:

- `game_created`;
- `player_joined`;
- `player_left`;
- `player_kicked`;
- `chat_message_sent`;
- `game_started`;
- `mole_selected`;
- `mole_targets_generated`;
- `player_received_share`;
- `ceo_selected`;
- `voting_round_started`;
- `vote_submitted`;
- `voting_resolved`;
- `decision_accepted`;

## Технические ограничения и MVP-допущения

- Нет настоящей auth/session системы: используется `current_user_id`.
- Игрок может отправить только одно действие голосования в рамках соответствующей фазы.
- Governance proposal или skip нельзя изменить.
- Мажорные решения не имеют отдельных механических эффектов, кроме истории, условий победы, удаления из доступных решений и бонуса голосовавшим из резерва.
- Governance предложения валидируются backend-ом, frontend не должен рассчитывать game logic самостоятельно.
- Все долевые операции используют целочисленные bps.
- UI может показывать проценты с дробной частью, но backend принимает целые bps.
- Авто-выход при закрытии вкладки использует browser best-effort механизм `pagehide/sendBeacon`; это удобно для локальной игры, но не является полноценной presence/session системой.
